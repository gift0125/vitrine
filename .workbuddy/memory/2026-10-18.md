# 2026-10-18 — M2 遗留项清理

## 1. 播放列表当前曲目高亮（真缺陷，已修）

**根因**：行标题用 `theme.primary` 着色，而 gpui-component 默认主题里 primary 与正文色几乎重合
（light: `primary.background=neutral-900` vs `foreground=neutral-950`；dark: `neutral-50` vs `neutral-50`），
等于没有区分度。`ListItem::confirmed()` 本身**不产生任何视觉**（只有传了 check_icon 才画对勾），
所以"当前曲目"实际只靠一个几乎无效的文字颜色。

**改法**（`crates/app/src/playlist.rs`，只用主题 token，不写死色值，方便 Stage 5 换肤直接受益）：
- `ListItem.bg(theme.list_active)` 行底色（light `#bfdbfe33` / dark `#1e40af33`）
- 行内首列 2px 强调条 `theme.list_active_border`（非当前曲目为 `transparent_black()` **常驻占位**，避免行内容左右跳动）
- 图标 `Music` → `Volume2`（"正在播放"语义），颜色 `list_active_border`
- 标题 `FontWeight::SEMIBOLD`
- 顺手补 `accessibility_label`（含"（正在播放）"后缀），`ListItem` 文档明确说没有 label 的行对读屏软件无名称

**验证**：浅色 `docs/screenshots/fix-02-playing-light.png`、深色 `fix-03-dark-video.png`、空闲 `fix-01-idle-light.png`
（空闲态确认强调条透明、无布局位移）。

## 2. 「空闲约 13 分钟后进程自行退出」→ 定性为**宿主进程树清理**，非应用缺陷

加了会话留痕（`crates/app/src/persistence.rs::log_session`）：
`%APPDATA%/simple-media-player/session.log`，记录 `start` / `app_quit requested` / `player_view dropped` /
`event loop returned` / `panic`（panic hook），超过 256 KiB 整体重写。时间戳自带 UTC 换算
（`civil_from_days`，不引入 chrono；补了 3 个单测）。

**关键发现**：`cx.on_app_quit` **只在显式 `App::quit()` 时触发，窗口关闭这条路径不走它**
（gpui 的 `App::shutdown` 才跑 quit_observers）。所以 mpv 回收实际靠 `VideoEngine::drop`
——实测播放中优雅关窗口，mpv.exe 确实消失，无孤儿。

**实测证据**：
- 作为**短命任务的子进程**启动（`cmd //c start`）：<60s 内消失，日志只有 `start` 一行、无 Drop、无 loop returned
  ⇒ 被外部**硬杀**，且正好发生在启动它的 bash 任务结束时。
- 作为**长寿命任务的子进程**启动：连续存活 **16m10s**（跨过 M2 的 13m27s 退出点），期间无任何退出日志。
  ⇒ 应用没有自杀路径；之前观测到的退出都来自宿主清理。
- 优雅关窗口（`taskkill //IM`）：日志 `start → player_view dropped → event loop returned`，mpv 同步回收。

**结论**：应用内不存在退出调用（全仓 grep 无 `cx.quit()`/`close_window`）；M2 那次"自行退出"是宿主清理，
带 Drop 的是优雅关窗清理、不带 Drop 的是硬杀。埋点保留，后续异常可直接分辨。

# 2026-10-18 — M3：Stage 5 打磨与发布（v1.0.0）

## 1. 错误提示（Toast）端到端打通

**结构性难点**：`play_track` / `start_video` 都拿不到 `&mut Window`，而 `window.push_notification`
必须要 window。**解法**：队列 + 在 100ms 的 `tick()` 里统一 flush。`tick` 本身有 window，且每 100ms 必跑一次，
延迟上限就是一帧感知（~100ms），用户完全看不出来。

`player_view.rs` 新增字段与方法：
- `pending_errors: Vec<SharedString>` / `pending_infos: Vec<SharedString>` / `last_error: Option<SharedString>`
- `report_error(msg)` → 同时 `eprintln!` + 记 `last_error` + 入队（`last_error` 主要给测试断言，也是未来状态栏的接口）
- `report_info(msg)` → 只入队
- `flush_errors(window, cx)` → `std::mem::take` 后逐条 `window.push_notification(Notification::error/info(msg), cx)`

覆盖到的失败路径（全部有用户可见文案，不再只是 `eprintln`）：
| 场景 | 文案 |
|---|---|
| 音频设备初始化失败 | `音频设备不可用：{err}`（构造时即弹） |
| 播放时无引擎 | `音频设备不可用，无法播放音乐（视频不受影响）` |
| 音频打开/解码失败 | `无法播放「{title}」：{err}` |
| 找不到 mpv.exe | `视频不可用：未找到 mpv.exe（设置 SMP_MPV_PATH 可指定路径）` |
| 拿不到 HWND / 叠加窗创建失败 / 进程启动失败 | 各自独立文案 |
| 视频加载/解码失败 | 见下节，分「文件没了」和「mpv 解不了」两种 |
| 导入文件/文件夹为空 | `未找到可播放的媒体文件` / `该文件夹内没有可播放的文件`（info 级） |

## 2. 视频错误详情透传（player-core）

`VideoStatus` 新增 `pub error: Option<String>` + `pub fn take_error(&self) -> Option<String>`（UI 取走即清空，
避免重复弹窗）。`end-file` 事件现在解析 `file_error` 字段：

```rust
"end-file" => {
    let reason = value.get("reason").and_then(|r| r.as_str()).unwrap_or_default();
    st.finished = reason == "eof";
    if !st.finished && !matches!(reason, "stop" | "quit" | "redirect") {
        let detail = value.get("file_error").and_then(|v| v.as_str()).unwrap_or_default();
        st.error = Some(if detail.is_empty() { … } else { format!("{reason}: {detail}") });
    }
}
```
`start-file` 里 `st.error = None`（换片清掉上一片的错误）。

UI 侧 `tick_video` 顶部先查 `take_error()`，再用 `Path::exists()` 分流：文件不在 →
`无法播放「x」：文件不存在或已被移动`；文件在 → `无法播放「x」：mpv 无法加载该文件（error: loading failed）`。
弹完自动跳下一首（列表没了就 stop + 隐藏叠加窗），不会卡死在坏文件上。

新增 3 个单测：`end_file_error_exposes_detail` / `normal_end_reasons_are_not_errors` / `start_file_clears_previous_error`。

## 3. 诊断开关（这次真的救了命，保留）

- `SMP_MPV_LOG=<path>`：把 mpv 的 stderr 重定向到文件（原来直接 null）。
- `SMP_MPV_TRACE=<path>`：把 JSON IPC 双向报文逐行落盘（`-> 命令` / `<- 事件`），`OnceLock<Option<Mutex<File>>>`。

**实际案例**：release 版所有视频一律 `mpv: error`，而 debug 版正常。`SMP_MPV_LOG` 抓到的是**空文件**

<- {"event":"end-file","reason":"error","file_error":"loading failed"}

**教训**：mpv 对路径里的重复分隔符不宽容；`playlist.json` 里出现 `C://` 必然 `loading failed`，已写进 README 故障排查表。

## 4. 无障碍（AccessKit）

原则：**纯图标按钮必须有 `accessibility_label`**，否则读屏软件读出来是个无名按钮。

- 添加文件 / 添加文件夹 / 清空播放列表 / 上一首 / 下一首 → 静态标签
- 播放/暂停 → 动态（"播放" ↔ "暂停"，切换后立即更新）
- 影院模式 → 动态（"进入全屏" ↔ "退出全屏"）
- 主题 → 动态（"切换到浅色主题" ↔ "切换到深色主题"）
- 播放列表每行删除按钮 → `从播放列表移除 {title}`（带曲名，否则 20 行读起来全一样）

**上游硬限制**：gpui-component 0.7.3 的 `Slider` 既没有 `FocusHandle`，也没设 ARIA role/value，更不支持键盘。
组件层改不了，只能在容器上套 `div().id("seek-bar").aria_label("播放进度")` / `aria_label("音量")` 给个分组语义，
并如实写进「已知限制」。这是本版本唯一没做到位的无障碍项。

## 6. 依赖冲突（`Cargo.lock` 手术）

加 `gpui-kit = { features = ["test-support"] }` 作 dev-dependency 后 `cargo build` 报
`failed to select a version for cocoa`：`test-support` 拉进 `gpui-fast-platform` → `gpui-fast-macos`
要求 `cocoa =0.26.0`，而既有 lock 为 `gpui-pre-macos` 钉了 `cocoa 0.26.1`；`unicode-properties` 同样撞车。

`cargo update -p X --precise Y` 卡死循环（改 cocoa 就撞 unicode-properties，反之亦然）。
**解法**：直接从 `Cargo.lock` 里删掉 `cocoa 0.26.1` / `unicode-properties 0.1.4` / `generic-array 0.14.9`
三个 `[[package]]` 块，让 cargo 一次性重解 → 落到 `cocoa 0.26.0` / `unicode-properties 0.1.3`。
只影响 macOS/wasm target，Windows 构建不受影响（备份在 `/tmp/Cargo.lock.bak`）。
**教训**：`cargo update` 的逐包降级在互相咬死的依赖图上无解，删块重解是可行退路。

# 2026-10-18 — 设计稿样式对齐（M3 后补做）

## 1. 根因：一直用的是 gpui-component 默认中性灰主题

设计稿（Ardot `737444551354649`）的名义色板是 **Catppuccin Latte + 单一 Mauve `#8839EF`**，
但 Stage 1–5 的实现从头到尾读 `cx.theme()` 的默认 token（neutral 灰），所以
`primary` 与正文色几乎重合（之前 M2 修的"当前曲目高亮"就是这个坑的表象）。
**"样式差别很大"不是细节没调，是整套色板没接上。**

## 2. 落地：`crates/app/src/theme.rs`

把设计稿色板翻译成 gpui-component 的语义 token，界面代码只读 token：

```rust
let mut cfg = ThemeConfig { name, mode, font_family: "Noto Sans SC", radius: 8, shadow: false, ..Default::default() };
cfg.colors.background = "#EFF1F5";   // Base
cfg.colors.border     = "#CCD0DA";   // Surface0
cfg.colors.primary    = "#8839EF";   // Mauve
...
Theme::update(cx, |t| { t.light_theme = light; t.dark_theme = dark; t.apply_config(&light); });
```

**API 坑**：
- `ThemeConfigColors` 里 `blue/red/green/cyan/magenta/yellow`（+ `_light`）是**私有字段**，
  结构体字面量 + `..Default::default()` 在 crate 外编译不过 → 只能先 `ThemeConfig::default()`
  再逐字段赋值（或者用 serde 从 JSON 反序列化）。
- `Theme::change/update` 的 `installed_by_edit` 判断：**不要在同一个 closure 里既换 mode 又换 config**，
  否则它认为"已经装过了"而跳过 `apply_config`。先 `update` 装配置，再单独 `change(mode)`。
- 缺失的 token 会回落到该模式的内置 `ThemeColor::light()/dark()`，所以只需覆盖用到的那些。

## 3. 布局/尺寸也按设计稿重排

## 4. 刻意不跟设计稿的三处（架构约束，不是偷懒）

设计稿里歌单是**浮在视频上的玻璃面板**、控制栏浮在视频底部。但 mpv 渲染在独立顶层窗口里，
会盖住任何 GPUI 控件，所以：视频只占歌单左侧、控制栏在视频下方、右侧 CC/音轨/设置/PiP 图标因无功能不画。
三条都写进 README「视觉规范」。

## 5. 截图工具：DPI 感知是必须的

`scripts/shot.py`（新增，支持 `--dark` / `--click "x,y"` / `--w --h`）：
- **不声明 DPI 感知就拿不到正确坐标**：Python 进程默认 96dpi 虚拟化，`GetClientRect`
  返回缩放后的尺寸、`ImageGrab` 只截到窗口左上角一块（症状：界面上只剩封面，歌单和
  控制栏"消失"）。开头必须 `SetProcessDpiAwareness(2)`。
- 窗口按**逻辑尺寸 → ×scale → 物理像素**设置，截完再缩回逻辑尺寸，高 DPI 下也是 1:1 清晰图。

|---|---|---|

| Windows | `2:307` | `12:12` 快退组 / `12:17` 快进组，同样 index 1 与 3 |

## 2. 图标规格

- 容器 **24×24**（比既有的 20×20 上一集/下一集大一级——要容纳「10」数字，20 塞不下）。
- SVG：圆弧半径 9、`stroke-width` 1.6、缺口 90°、箭头位于弧端点沿切线方向；色 `#4C4F69`。
- 数字「10」是**独立的 TEXT 节点**（Inter Medium 8px，x7.6 / y7.4）叠在弧心，**不能用 SVG `<text>`**——字体依赖不可靠，导出时会掉字。

## 3. 踩坑：SVG 镜像不能用 `<g transform="scale(-1 1)">`

写了 `transform="translate(24 0) scale(-1 1)"` 包住路径做快进图标，Ardot 解析后报
**degenerate geometry（0×0 / out of frame bounds）**，图标节点插入失败（`12:7`、`12:18`），
但外层 frame 和数字节点却成功了 → 表现为"空的组"（只有数字没有箭头），排查时容易误以为布局问题。

**正确做法**：手算镜像 path，`x → 24-x`，并翻转 arc 的 sweep-flag。
- 快退：`M12 3A9 9 0 1 0 21 12` + 箭头 `M11.8 3.2L15.2 0.9L15.2 5.5Z`
- 快进：`M12 3A9 9 0 1 1 3 12` + 箭头 `M12.2 3.2L8.8 0.9L8.8 5.5Z`

## 4. 验证

截 `2:236` / `2:307` / `2:58` 三张全部通过：五件套居中协调，圆弧缺口方向正确（快退缺口在右上箭头朝左、快进镜像），左右控制组未被挤压（中部实际加宽 72px，剩余约 880 仍充裕）。

## 5. 播放控制居中 + release 不再弹 cmd

用户两处反馈：① 走带按钮没居中；② 双击 exe 先闪一个 cmd 窗口。

**① 居中**：原布局 `justify_between` 把走带和音量塞在同一个左侧组，右侧只有两个图标，
宽度不等 → 走带被挤到偏左。改成三段式：左音量 `flex_1`（靠左）、中间走带 `flex_shrink_0`、
右侧全屏+换肤 `flex_1`（靠右）。两侧同为 `flex: 1 1 0%` 等宽 → 中间栏数学上必落在窗口正中。
实测截图播放按钮圆心 519.5 vs 图像中心 520.0。新增 UI 测试 `transport_controls_are_horizontally_centered`
（圆心偏移 ≤1px + 两侧间距对称），防回归。

**② 控制台窗口**：Rust bin 默认按 console 子系统链接，双击先开 cmd。加
`#![cfg_attr(all(not(debug_assertions), target_os = "windows"), windows_subsystem = "windows")]`
——release = PE subsystem 2（GUI），debug 仍是 3（保留控制台看 `eprintln!`）。
验证方式：读 PE 头 `OptionalHeader.Subsystem`，不是靠肉眼。
副作用是 release 没有 stderr，所以 `report_error` 现在**同时**写 `session.log`（`error: ...` 行），
用户报障至少有据可查。另用探针程序确认：GUI 子系统 + 无控制台句柄时 `eprintln!`/`println!`
不会 panic（std 把空句柄当空设备），所以不用给所有打印加保护。

**截图工具的第二个坑**：`SetWindowPos` 设的是**外框**尺寸（1560×1020 只得到 1538×964 客户区），
再用 `ImageGrab` 截客户区会拉伸变形、边距对不上。改用
`AdjustWindowRectExForDpi` 反推外框，并按 0.1s 轮询等窗口外框位置稳定后再截
（DWM 动画期间抢截会在图左边留一条黑边）。现在 `client=` 恒等于目标逻辑尺寸 × 缩放比。

## 9. 视频「有声音、黑屏」根因（重要，别重复排查）

真因不在 mpv：

1. `h_flex()` **默认 `items_center`**；舞台的子元素全是绝对定位（内容高度 0），

2. 视频区的 `canvas` prepaint 拿到 `bounds = 1040x0`（y=302，正好是中间区域垂直居中的位置），

3. 叠加窗永远停在 `(0,0,0,0)` + `visible=false` ⇒ 黑屏但有声音。

**修法**：舞台加 `.self_stretch()`（`align-self: stretch`）。修完 bounds = `0,34 1040x536`，
叠加窗 `(0,46,1560,850) visible=True`，画面与进度都对上了。

**排查手法（可复用）**：临时把 canvas prepaint 的 bounds 写进 `session.log`，
再 `EnumWindows` 对比 mpv/叠加窗的 rect——两边一对照就知道是"没算出来"还是"算错位置"。

**回归用例**：`stage_fills_space_between_title_band_and_bottom_band`
（舞台 `id="stage"` + `.test_support()`，断言高度 > 窗口一半、横向铺满、上下留出标题带与胶囊）。

### 13.1 拖放：原来根本没接监听

GPUI 的拖放链路（读 gpui-pre 源码确认）：`FileDropEvent::Entered{position, paths}`
→ `cx.active_drag = AnyDrag{ value: Arc<ExternalPaths>, .. }` → `Pending`/`Entered`
都转成一次 MouseMove → `Submit` 转成 MouseUp → **鼠标下 hitbox 的 drop listener**
被调用（条件：`drag.value.type_id()` == listener 的 `T`，且 `hitbox.is_hovered`）。

所以根节点挂 `.on_drop::<ExternalPaths>(...)` 就等于「整窗可投放」——之前一行都没写，
自然"拖进去毫无反应"。

**两个卡点（都已实测，别再试）**：
- `cx.active_drag` 是 `pub(crate)`，应用侧读不到拖拽状态，不能轮询；
- `ExternalPaths(pub SmallVec<[PathBuf;2]>)` 字段虽 pub，但 gpui-kit 不 re-export smallvec，
  **要构造就得自己加一份 `smallvec = "1"` dev-dependency**（版本会被 cargo 统一到 1.16.3）。

**叠加窗口挡住的 80% 面积**：OLE 找投放目标是 `WindowFromPoint` + 沿**父链**向上，
断在叠加窗口就完事（GPUI 的 `RegisterDragDrop` 在主窗口上，够不到）。实测
`WindowFromPoint` 在视频中心返回的是 `SimpleMediaPlayerVideoOverlay`，而且
**加 `WS_EX_TRANSPARENT`（无论加在自己还是 mpv 子窗口上）都不会改变 WindowFromPoint**——
那条路子不通，别浪费时间。正解是叠加窗口自己收：`DragAcceptFiles(hwnd, TRUE)`，
exstyle 会带上 `WS_EX_ACCEPTFILES`(0x10)，系统据此把投放转成 `WM_DROPFILES`；
wndproc 里 `DragQueryFileW` 取路径 → `Mutex<Vec<String>>` 队列 → 100ms tick 消费
（wndproc 里没有 `App`，不能直接改视图）。

**提示层为什么用时间戳**：`drag_over::<ExternalPaths>` 的回调只给 `&StyleRefinement`，
拿不到 `Context`：不能改普通字段、不能 `notify`。所以回调里只写
`Cell<Option<Instant>>`，tick 里判断「250ms 内还有时间戳 = 还在拖」再 `notify()`。
拖走时不再有时间戳，提示自动熄灭——比依赖 `on_file_drop_exit` 稳（那个只给 `&mut App`，
且只对 `Exited` 且元素仍 hover 时才触发）。

**视频模式下提示层要换位置**：全窗压暗 + 居中卡片会被 mpv 叠加窗整个挡住
（等于没有），所以视频模式只在 34px 标题带里放一枚小胶囊。

### 13.2 窗口按钮

`IconName::WindowMinimize/Maximize/Close` 是 24 网格 + 2px 描边，缩到 10px 描边只剩
半个像素 → 栅格化成一团糊。改成手写 10×10 SVG（1px 描边），
`Icon::default().data(SVG).size(px(10.))`；按钮 46 宽 × 标题栏高，悬停铺满底色，
关闭键 `#C42B1C` + 白图标，最大化时按 `window.is_maximized()` 换还原字形。

### 13.3 胶囊比例 + 标题带对比度

padding 20×12 → 16×8、圆角 14 → 12、行距 6 → 4、进度容器 12 → 10、时间码 11 → 10，
实高 107 → ~90（680 高窗口 15.7% → 13%），`BOTTOM_BAND` 132 → 116。

顺带发现：视频模式整块 chrome 是深色画布，标题带/窗口按钮却还在取浅色主题的

### 13.4 验证

- 新增 UI 用例 `dropping_files_adds_them_and_starts_playback`：
  `window.dispatch_event(FileDropEvent::Entered/Submit)` 打进无头窗口，
  断言入列表 + `current == Some(0)`。**这是唯一能覆盖 GPUI drop 链路的办法**。
- 叠加窗口路径：`PostMessage(WM_DROPFILES)` + 手工拼 `DROPFILES`（pFiles=20、fWide=1、
  双 NUL 宽字符）→ `session.log` 出现 `drop 1 path(s): C:/.../gen-1080p.mp4`，且画面切过去。
- `GetWindowLong(GWL_EXSTYLE)` 运行时确认为 `0x8000090`（含 ACCEPTFILES）。
- 真实 OLE 拖源（ctypes 手搓 `IDropSource` 虚表 + `SHCreateDataObject`）能造出投放，
  但 `DoDragDrop` 的模态循环在自动化环境里不返回（要真人松手），故没做成常驻测试。
  注意：`SHCreateDataObject` 的 `apidl` 必须是**child PIDL**（`ILFindLastID`），
  传整条绝对 PIDL 会得到一个相对路径的 CF_HDROP（踩过，表现为"文件不存在"）。
- `cargo test --workspace`：15 + 16 全绿；clippy 0 告警。

## 14. 提示的两种呈现 / 按钮悬停条（第三轮反馈）

用户：「打开视频文件时，弹出一条 toast 即可，不需要展示在窗口右侧；最大化、最小化在鼠标放上去时，

- `flush_errors` 按**底色**分流：`video_active` → `status_pill: Option<(SharedString, Instant, bool)>`；

## 15. 字体与任务栏图标（第四轮）

用户问：「title 字体在 win 上默认是否用雅黑更好？在 win 的任务栏上显示时，没有 logo。」

### 15.1 字体：设计稿字体 Windows 不预装

`theme.rs` 原来写死 `Noto Sans SC`（Ardot 设计稿字体）。本机装过 → 看不出问题；
但 Windows 不预装，发行包到别人机器会退到系统兜底（中文常落宋体，11px 笔画发糊）。

改成平台原生：Windows `Microsoft YaHei UI` / macOS `PingFang SC` / 其他 `Noto Sans SC`；
等宽同理（Consolas / Menlo / DejaVu Sans Mono），并把 `player_view` 里写死的
`MONO_FONT` 收编进 `theme::mono_font_family()`（写死会让 mac/linux 退到非等宽，时间码宽度乱抖）。

选型做了三方同帧对比（Noto / Segoe UI 主族 / 雅黑）：Segoe 主族时 CJK 走系统回退、
结果随机器变；雅黑主族确定且中英同一字面。用例
`ui_font_is_a_system_font_not_a_design_tool_font` 守住「不许用设计稿专用字体」。
（`theme.rs` 的 `ThemeConfig.font_family` 改一处即全局生效——`root.rs` 会
`.font_family(cx.theme().font_family)` 铺到整棵树。）

### 15.2 任务栏没有 logo：PE 缺 ID=1 图标组

GPUI `gpui-pre-windows::load_icon` 用的是
`LoadImageW(module, MAKEINTRESOURCE(1), IMAGE_ICON, …, LR_SHARED)` —— **只认 ID=1**。
没有这条资源就返回空句柄 → 窗口类无图标 → 任务栏/Alt+Tab 显示系统占位图。
`WindowOptions.icon` 是 x11 only，指望不上。

方案：`scripts/make-icon.py`（PIL，1024 超采样 → 16…256 多尺寸 ico，紫底+白三角）
+ `crates/app/build.rs` 用 `embed-resource`（`[target.'cfg(windows)'.build-dependencies]`）
写 `1 ICON` + VERSIONINFO。rc.exe 找不到时只 warning。

**坑**：`fs::canonicalize` 给的是 `\\?\C:/...`，写进 `.rc` 会被 rc 的 `\\` 转义吃掉，
报「找不到文件」且没有更多信息。去掉前缀 + 换正斜杠即可。

验证三层：`FindResourceW(1, RT_ICON/RT_GROUP_ICON/RT_VERSION)` 都存在；
`GetClassLongPtrW(GCLP_HICON)` 非 0（实测 `0x8DA0B95`）；截任务栏按 Mauve 定位确认图标。

### 15.3 顺带：SMP_DATA_DIR + 不污染用户数据

这轮为了拍中文标题直接改了 `%APPDATA%\simple-media-player\playlist.json`，
把用户正在用的列表覆盖了（他当时正开着 app 看片子）。补救：加了 `SMP_DATA_DIR`
环境变量可整体挪走配置目录，截图/验收从此都跑临时目录。
教训：**验收脚本要跑在隔离数据目录上**，别动真实 appdata。

另：观察到一个 `thread '<unknown>' has overflowed its stack`（某次被 TerminateProcess 的实例），
正常关闭（WM_CLOSE）复测是干净退出（exit 0，session.log 有 `player_view dropped` +
`event loop returned`），跑 20s 也不复现，暂记为「强杀时的收尾噪音」。

## 16. 画面上的 chrome：给叠加窗口开洞（第五轮）

用户四句话：「顶栏和控制栏未悬停在视频上方；拖放进去时，不用通知了；播放列表在视频上方，
不挤视频位置；鼠标左键点中视频时，可以拖动窗体。」

### 16.1 根因：不是布局问题，是 z 序问题

视频画面是**另一个顶层窗口**（mpv 的 `WS_POPUP` 叠加窗）画的，它永远盖在 GPUI 主窗口之上。
所以之前只能「让位」：画面缩在标题带以下、胶囊以上，歌单展开再让出右侧 344px。
用户要的是「画面占满整窗、控件浮在画面上」，让位方案本质做不到。

### 16.2 正解：`SetWindowRgn` 从叠加窗身上挖洞

窗口区域同时裁剪**渲染**和**命中测试**，挖掉的区域会露出下面的 GPUI 主窗口 →
标题带/胶囊/歌单就真的压在画面上了。

```rust
region = CreateRectRgn(0,0,w,h);
for hole in holes { cut = CreateRoundRectRgn(...); CombineRgn(region, region, cut, RGN_DIFF); DeleteObject(cut); }
SetWindowRgn(hwnd, region, 1);   // 成功后 region 归系统所有，不要再 DeleteObject
```

- `CreateRoundRectRgn(l,t,r,b,ellipseW,ellipseH)` 收的是椭圆**宽高（直径）**，不是半径；
- 区域是**物理像素**，且 `SetWindowPos` 改尺寸**不会**重算区域 → `set_rect` 后要重新应用；
- 空 holes = `SetWindowRgn(hwnd, 0, 1)` 恢复整窗（退出视频模式时调）；
- 挖的矩形外扩 1.5px，否则圆角/描边会被切掉半个像素。

`render()` 顺序跟着倒过来：视频舞台先声明（`absolute` 铺满整窗），chrome 全部排在它后面
（GPUI 按子节点声明顺序绘制，后画的在上）。

胶囊高度是内容撑开的，写死会偏 → 胶囊里放一个 `canvas` 每帧把 bounds 写进 `capsule_rect`，
`chrome_holes()` 用它算洞。`set_holes` 按内容去重，避免 100ms tick 反复打系统调用。

### 16.3 按住画面拖窗体

叠加窗 wndproc 收 `WM_LBUTTONDOWN` → `GetWindow(hwnd, GW_OWNER)` 拿主窗口 →
`ReleaseCapture()` + `SendMessageW(owner, WM_NCLBUTTONDOWN, HTCAPTION, 0)`。
把这一下「转交」给系统当标题栏拖动，贴边吸附/最大化还原/跨屏都白拿；
叠加窗自己由 tick 追上。

### 16.4 拖放不再弹提示

删掉 `append_dropped_and_play` 里的「已导入 N 个文件 · 正在播放「xxx」」。
拖进来本身就是意图，画面换了就是回执。（列表为空仍保留「没有可播放的媒体文件」。）

### 16.5 验收脚本（`scripts/verify_floating_chrome.py`）

取样判据：`(lw/2, 40)` = 画面蓝 `(0,0,78)`；`(8,17)` = 画布深色 `(8,9,12)`；
`(40, lh-60)` = 玻璃深色 `(10,11,14)`；点列表键后面板内 = `(231,227,245)`；
真实鼠标拖画面 → 窗口位移 `(144,72)`。

两个坑（可复用）：
- 逻辑尺寸要按**实测客户区**换算：`SetWindowPos` 设的是外框，实测 1898×1189 物理 ÷1.5
  = 1265×793，不是设的 1280×800。按目标尺寸换算会整体偏几像素，点 28px 图标正好进间隙。
- 交互验收一律 `SetCursorPos` + `mouse_event`。`PostMessage(WM_LBUTTONDOWN)` 的 lparam
  不总被采信（命中测试用真实光标），这条以前记过，这次又栽了一次。

### 16.6 新用例

`video_mode_floats_chrome_over_a_full_window_picture`：视频模式下 stage 四边贴窗口、
进度条在 stage 内部、展开歌单后 stage 宽度一像素不变。

### 16.7 残留

洞露出来的是 GPUI **不透明**画布，不是画面本身 → chrome 是实心深色，不是设计稿的毛玻璃
（GPUI 的 Windows 后端 DComp + `WS_EX_NOREDIRECTIONBITMAP` 不支持窗口级透明）。
歌单面板仍用应用表面色（Latte 浅底）：改深底的话 `List` 的行文字（取主题 token）不可读。

## 17. 最大化之后点不回来（第六轮）

用户：「最大化之后，再点不能恢复原窗口大小。」

### 17.1 根因：`zoom_window()` 只最大化，不还原

`gpui-pre-windows 0.3.9` 的 `zoom()` 只有一句 `ShowWindowAsync(SW_MAXIMIZE)`。
而 `is_maximized()` 是对的（`IsZoomed`），所以图标会变成「还原」、点下去却毫无反应。
自己写 `window_actions::{is_zoomed, set_zoomed}`。

### 17.2 第一版用同步 ShowWindow 踩了更深的坑

同步 `ShowWindow` 在 GPUI 的事件派发里**重入 `WM_SIZE`**，GPUI 这一层不会因此重新布局：
窗口真变成 3840×2088，界面还画在 1040×680 上 → 右边一片空白、hitbox 全在旧位置，
「再点一次」永远点不到按钮。

判别方法（可复用）：日志里 toggle 只出现一次 + `GetClientRect` 已经是新尺寸 +
截图里界面只占左上角 = 布局没跟上。

修法：`ShowWindowAsync`（命令投回消息队列，当前事件派发结束后再处理），
布局就正常跟上了 → 点「还原」立刻回到 1898×1189。

### 17.3 异步的配套

- `maximized` 先乐观更新（`target = !self.maximized`）；
- `zoom_pending: Option<Instant>` 记时间，tick 在 300ms 内不做反向纠正（否则图标闪一下）；
- tick 每帧比对 `IsZoomed` → Aero Snap / Win+↑ / 右键菜单改的状态也能被图标跟上；
- 双击标题栏不用写代码：拖拽区映射 `HTCAPTION`，Windows 原生就做最大化/还原
  （实测不走 `on_double_click`，日志里没有 toggle 记录）；
- 顺带：最大化时不再把最大化尺寸当用户尺寸存进 settings。

### 17.4 GPUI 到底支不支持窗口透明（用户问的）

不是版本问题。gpui-pre 0.3.6 已有 `WindowBackgroundAppearance::{Transparent, Blurred,
MicaBackdrop, MicaAltBackdrop}`；`WindowOptions.window_background` 可设，
`Window::set_background_appearance` 可运行时改；非 Opaque 时渲染器把后备缓冲清成 alpha 0；
Windows 后端 `Blurred` → `SetWindowCompositionAttribute(accent_state = 4)`（acrylic）。

但它模糊的是窗口**背后**的内容，我们的视频画在**上面**那个叠加窗里 → 无效。
要用就得反转 z 序（owned 窗恒在 owner 之上，必须放弃 ownership 自己管 z 序），
属重构级改动，这一轮不做。

- 提交 `3c43976`（fix(window)：新增 `crates/app/src/window_actions.rs`，改 player_view / main / ui_tests / README / plan / 验收脚本）。
- `scripts/package.ps1` 重打包 → `dist/simple-media-player-1.0.0.zip`（8.7 MB，PE Subsystem = 2 仍是 GUI）。
- 对**打包后的 exe** 复跑 `scripts/verify_floating_chrome.py`（`SMP_EXE=` 覆盖）：
  `ALL OK`（标题带深色 8,9,12 / 最大化后 3840x2088 / 再点回 1898x1189 / 画面拖动位移 144,72）。
- 版本事实核对：crates.io 上 gpui-kit 最新 0.7.3（我们就是）、gpui-pre 最新 0.3.9

## 18. 第七轮：视频窗挪到主窗下面（用户：「视频窗放在主窗下听起来更像正解」）

### 18.1 方向对，但方案被实测推翻了三次

先做 20 行实验确认**逐像素透明是支持的**（`window_background = Transparent` + 一块红方块，
整窗透出后面的浏览器）。之前"GPUI 不支持窗口级透明"的结论是错的。

1. 第一版只把根节点改透明 → 截图仍是 `#EFF1F5`。真凶是 gpui-component 的
   `RootPlugin::style` 给**每个窗口表面** refine 了 `.bg(tokens.background)`。
   `Root` 实现 `Styled`，实例 refine 在插件之后 → `Root::style().refine(...)` 逐窗覆盖。
   必须在 `render` 里做（`new` 时 Root 还没挂窗口；无头测试没有 Root，要 `flatten()` 守卫）。
2. 透明了画面还是黑的 → **三次实验**定位：移开叠加窗画面就正常；在主窗区域挖 300×300 的洞，
   画面正好出现在洞里。**系统判定遮挡只看窗口矩形/区域，不看逐像素 alpha**，
   被判 100% 遮挡后 mpv 停止出帧（`PrintWindow` 也黑，`--d3d11-flip=no` 无效）。
3. 于是主窗口要把画面区从**窗口区域**里减掉：`整窗 − stage + chrome(RGN_OR)`。
   非客户区边框留在区域里 → 缩放/拖动照常；chrome 必须加回去，否则自己也被剪
   （区域同时裁剪渲染与命中测试）。

### 18.2 三个"捷径"全是坑

- 给叠加窗加 `WS_EX_TRANSPARENT`（想命中穿透）→ 整窗不再被合成，帧在、看不见。
- 把舞台挂 `WindowControlArea::Drag`（想白拿原生拖动）→ 舞台压根不在主窗区域里，GPUI 收不到。
- `SendMessageW(main, WM_NCLBUTTONDOWN, HTCAPTION)`（想白拿贴边吸附）→ 拖动只跟上头一两步
  （GPUI 的 wndproc 吃掉 `WM_MOUSEMOVE`），紧接着的双击被当成"继续拖动"，窗口挪一段而不是最大化；
  转交 `WM_NCLBUTTONDBLCLK` 又会丢 `WS_MAXIMIZE`（撑满工作区但 `IsZoomed` 假，图标和"再点还原"全乱）。

最终：wndproc 里自己实现拖动（记起点 + `SetCapture` + 按累计位移 `SetWindowPos` 主窗，
叠加窗同步粘住，不等 100ms tick），双击走 `window_actions::set_zoomed(main, !is_zoomed)`。
窗口类必须加 `CS_DBLCLKS`，否则 `WM_LBUTTONDBLCLK` 根本不出现。

### 18.3 顺带修的

- 视频窗改铺主窗**外框**（`GetWindowRect`）而不是客户区：按客户区定位时左边/底部透出桌面
  （边框那圈还在主窗区域里，而我们在那儿不画东西）。
- 区域去重键**去掉窗口位置**（坐标相对窗口矩形，纯移动不用重设）：否则拖动时每帧
  `SetWindowRgn` → 整窗重绘、画面发抖。
- 标题带视频模式补 `overlay::glass()`：画面顶到窗口边时曲名直接压在亮画面上读不出来。
- `scripts/shot.py` 改成走 `SMP_DATA_DIR` 隔离 —— 这次截图才发现它一直在往**真实的**
  `%APPDATA%\simple-media-player\playlist.json` 里追加文件（已把本轮追加的两条清掉，
  其余条目原样保留）。

### 18.4 验收（脚本本身也重写了）

`scripts/verify_floating_chrome.py` 改成按新机制判定，10 项 `ALL OK`：

- 画面中心是彩条（区域减法生效才会出帧）+ `GetWindowRgn` = COMPLEXREGION 且外接框是整窗；
- 视频窗与主窗 `GetWindowRect` 逐像素相同（静止/最大化/拖动后三次）；
- 胶囊里压在两个不同色条上的两点色差 536（>25 才算"透出画面"，实心黑板会抹平）；
- 展开歌单后 `PtInRegion(面板中心)` 为真、面板取样是浅底 (231,227,245)；
- 双击画面 `IsZoomed` 真 → 再双击假；按住画面拖动位移 184,72、拖动途中画面中心仍是彩条。

脚本自身踩的坑：残留实例 → `FindWindowW` 拿到别人窗口（加了 pid 校验）；窗口尺寸按
`AdjustWindowRectExForDpi` 反推会多算一个标题栏（这类 `WM_NCCALCSIZE` 返回 0 的窗口），
改成"设一次 + 按实测客户区差值补两次"；`SetCursorPos` 到同一点不产生 `WM_MOUSEMOVE`，
点击会被丢（先停在旁边 40px 再挪进去）。

单测：`ui_tests::chrome_region_covers_capsule_and_panel`（区域矩形 vs 实际布局：

### 18.5 收尾：双击偶发被吞的真正原因

验收连跑时「双击画面最大化」大约三分之一概率失败。查下来不是判定问题，是应用真缺点：
叠加窗是 `WS_EX_NOACTIVATE`，系统不会替我们把主窗提到前台——**用户点画面既不会激活窗口，
"窗口在后台时的第一次点击"还会被系统当成激活吃掉**。修法：wndproc 里
`WM_LBUTTONDOWN` / `WM_LBUTTONDBLCLK` 先 `SetForegroundWindow(main)`（鼠标这一下投给了

- 歌单开合、双击最大化都改成「按结果重试」（`toggle_playlist(want)` / `wait_maximized`），
  重试仍不对才报失败；判据用「区域里有没有面板」「客户区尺寸变没变」，
  `IsZoomed` 只作参考打印；
- 启动时校验 `FindWindowW` 拿到的窗口 pid 是否属于本次启动的进程（残留实例会让坐标全错），

  的窗口上会多算一个标题栏高度）。

## 20. 实测：mpv 官方构建的 ISA 基线，v3 有没有提升（结论：本机没提升）

事实：mpv 官方 Windows 包全部来自 shinchiro（`mpv-winbuild-cmake`），只发布两个 x86_64 变体 ——
`mpv-x86_64-*`（通用基线 = **x86-64-v1 / SSE2**）与 `mpv-x86_64-v3-*`（要 AVX2）；
**没有 v4 变体**（要 AVX-512 只能自己编）。本机 `mpvio.install` 装的是通用版 v0.41.0（2025-12-25）。

实测 A/B（**同一 commit** `413ff0b1c`，20261004 两个包，避免版本漂移）：
`--no-config --no-hwdec --vo=null --ao=null --untimed --frames=1800 test-media/gen-1080p.mp4`（1080p h264）
- 通用：596 / 600 / 670 ms
- v3：602 / 616 / 637 ms
→ 差异落在噪声里，**0% 提升**。原因：ffmpeg 解码器主体是手写汇编 + `av_get_cpu_flags()` 运行时派发，
通用版在这颗 CPU 上照样跑 AVX2/AVX-512 内核；`-march` 只影响编译器自动向量化的 C 部分。
本机 1800 帧 ≈ 0.6s = **3000fps ≈ 100× 实时**，本来就不是瓶颈。

而且应用里 `hwdec=auto-safe` 实测选中 `h264-d3d11va`，解码在 GPU，CPU ISA 更无关。
结论：不换 v3；打包（`package.ps1 -WithMpv`）也应继续带通用版，否则老机器 illegal instruction。
真要提性能，杠杆在 `vo=gpu-next` / hwdec 零拷贝 / cache，不在编译选项。

工具备忘：本机无 7z，解 shinchiro 的包要 `7zr.exe`（py7zr 不支持 BCJ2）；临时解压在 `%TEMP%\mpvt`。

## 21. 第八轮：窗体大小 = 内容大小

用户要求：「窗口播放视频时，窗体大小等于内容大小，overlay 展示于视频上方」。
后半句第七轮已达成（chrome 真浮在画面上），这轮补前半句，顺手修双击。

**尺寸来源**：mpv `dwidth/dheight`（显示尺寸，已校正 SAR/旋转），不是 `width/height`
（编码尺寸，anamorphic 会拉扁）。订阅 id 5/6；`null` → 0（未解码）；`start-file` 清 0。

**策略**：纯函数 `window_actions::plan_fit(FitScene) -> FitPlan`，三条规则依次降级：
1:1 → 缩进工作区（留 12 逻辑像素）→ 比最小窗口还小就放大（避免黑边）；位置以窗口中心为
锚点再夹回 `rcWork`；外框-客户的边框差值实测。5 条单测。

**三个坑**（都记进 MEMORY.md 了）：
1. `SetWindowPos` 不能在 `Context::update` 里调 —— 同步派发 `WM_SIZE` → 重布局，而 App
   正被借用，布局停在旧尺寸 + hitbox 错位。丢进 `cx.spawn_in(...)` 前台任务即可。
2. mpv 的 `dwidth` **先报 0.75 倍的假值**（1280×720 → 先 960×540）。日志里抓到的：
   `fit_to_video: video=960x540 ...` 紧跟着 `video=1280x720 ... unchanged`。加 `fit_seen`
   （同值连报两次才动手）后只剩一行、无跳变。
3. 系统不给 `WS_EX_NOACTIVATE` 且从未激活的窗口发 `WM_LBUTTONDBLCLK` —— 即使类样式带了
   `CS_DBLCLKS`。改成自己判双击（`GetDoubleClickTime` + `SM_CXDOUBLECLK/Y`，坐标用
   `GetCursorPos` 的**屏幕坐标**，窗口在两下之间移动也不影响）。顺带放开"最大化时按住画面
   也能拖"（原来 `IsZoomed` 时直接无视）。

**z 序**：`set_rect` 不再"位置没变就 return"，改成每次 `ensure_below`
（`GetWindow(main, GW_HWNDNEXT) == overlay` 才不动）——查一次比每 100ms 打一次
`SetWindowPos` 便宜。

**一次差点误判**：验收脚本报 `FAIL: 画面右缘是 (255,255,255)`，怀疑主窗口玻璃把画面洗白了。

改成"对齐 + 最多 3 秒重试取样"后稳定通过。**教训：这类取样必须等 VO 重配完成。**

## 22. 视频模式加圆角

用户：「窗口播放时，加上圆角。」做法就一句 DWM 属性，关键是**两块窗口都得设**：

```rust
DwmSetWindowAttribute(hwnd, DWMWA_WINDOW_CORNER_PREFERENCE /*33*/, &DWMWCP_ROUND /*2*/, 4)
```

- 左上/右上角 = 主窗口的标题带；左下/右下角 = **下面那块视频窗**（主窗口在这一带的区域
  只剩悬浮胶囊）。只设主窗口 → 下面两角是方的；只设视频窗 → 上面两角被标题带方角盖住。
  两边半径都由 DWM 按 DPI 算，形状天然一致。
- 为什么不用 `SetWindowRgn`：区域是 1 bit 的，必有锯齿；DWM 这条按 DPI 算半径 + 抗锯齿，
  和系统其它窗口一个样。代价是 Win10 没有这条属性（`E_INVALIDARG`），静默忽略、保持直角。
- 进的时机：`create_overlay` 里给视频窗设一次；主窗口在 `sync_overlay_rect` 里按
  `corners_rounded != video_active` 切换（每帧都跑，但只在变化时调一次）。
  退出视频模式设 `DWMWCP_DONOTROUND`（1），音频模式维持原来的直角。最大化时系统自动不圆。

**验收**：像素判据不稳（角外是桌面），改成用 `DwmGetWindowAttribute` 读回属性值
（主窗/视频窗都是 2 才算过），再打一行"角上像素 / 往里 8px"给人眼复核：
`角上像素=(3,92,163) 往里 8px=(61,0,0)` —— 角上是桌面、往里 8px 是画面，圆角确实生效。
连跑 3 次 `ALL OK`（12 项）。

顺手两处加固：
- `scripts/shot.py` 新增 `--margin <逻辑像素>`：圆角与 DWM 阴影都在客户区之外，只截客户区
  看不见（截图里是一条直边）。留 margin 时窗口会被摆到 `(margin, margin)`，免得 bbox
  越过屏幕边缘被裁。
- 验收脚本在双击阶段前把窗口**摆回确定位置**（上一步拖动会把它拖到屏幕外，
  双击点算出来会落到别的窗口上，造成假失败）；`sample()` 越界改为返回黑色而不是抛
  IndexError（拖动途中截图偶尔会被屏幕边缘裁掉一块）。

`cargo test` 16 + 26 全绿；release 与打包版各跑一遍验收 → `ALL OK`。

# 2026-10-18（续）— 全屏播放：双击进、四个口子出、顶栏铺满

用户四连报障（原文）：「双击时，不是全屏播放。全屏播放后，最大化按钮回不到窗口。
顶栏没有铺满宽度。全屏后，esc不能返回窗口模式。」四条都已修，验收脚本 14 条 ALL OK。

## 1. 双击 = 全屏（不再最大化）
- 叠加窗是 `WS_EX_NOACTIVATE`，系统对未激活窗口**只连发两条 `WM_LBUTTONDOWN`**，
  `WM_LBUTTONDBLCLK` 常常不来 → 自己判双击（`GetDoubleClickTime` + `SM_CXDOUBLECLK/CY`）。
- 判双击的坐标**必须取消息 lparam**（`ClientToScreen`），不能用 `GetCursorPos()`：
  合成输入下真实光标在别处，两次坐标差半屏，双击永远不成立。
- wndproc 里没有 App/Window → 事件入 `static Mutex<Vec<OverlayEvent>>`，
  由 100ms tick 取出调 `PlayerView::set_cinema()`（和 `take_dropped` 同一套路）。

## 2. 全屏的四个出口：Esc / 再双击 / 右上角最大化 / 胶囊退出键
- `Esc` 用 `App::intercept_keystrokes`：`bind_keys`+`on_action` 无效——无焦点时 GPUI
  把按键派发给 dispatch 树的根（gpui-component 的 `Root`），实测返回 false。
- 「最大化」在全屏时先退影院：GPUI 全屏已摘掉 `WS_MAXIMIZEBOX`，再 `SW_MAXIMIZE` 只会错乱。

## 3. 顶栏没铺满 = 客户区没铺满窗口
- 隐形外框实测 1.5× 下「外框 − 客户区 = 22×11」（每边 7 逻辑像素）。子类化窗口过程拦
  `WM_NCCALCSIZE`，把左/右/下三边扩到窗口矩形（顶边不碰，GPUI 最大化时会故意下移）。
- 窗口矩形：`wParam != 0` 取 `rgrc[1]`；`wParam == 0` 取 `lparam` 所指 `RECT` 的**初值**
  （`CallWindowProcW` 会就地改写，要先抄）。**不能用 `GetWindowRect`**（进出全屏时读到旧值）。
- 铺满后边框变客户区 → `DefWindowProc` 不再认边框，自己补 `WM_NCHITTEST` 缩放热区
  （6 逻辑像素；最大化/最小化/全屏时跳过）。
- 连带修两处：① GPUI 用创建时记的 `border_offset` 算 `ptMinTrackSize`，720p 片子被顶成
  `720+11=731` → 拦 `WM_GETMINMAXINFO` 减掉；② 单纯改尺寸那一路 GPUI 不管
  （`wParam==0` 退回 `DefWindowProc`），两条路都改成铺满，就没有"改尺寸后抖一下"。

## 4. 最费劲的一条：进出全屏时 GPUI 丢掉自己的尺寸通知
- 现象：画面铺满，顶栏只在左上角画 853×34；右上角按钮**不存在**，点「最大化」无反应；
  `Esc` 反而正常（键盘不走命中测试）。
- 根因：`WM_SIZE` 在 `SetWindowPos` 里**同步**派发，此时 App 正被本轮 update 借用，
  GPUI resize 回调里 `handle.update()` 拿不到借用权、`log_err` 静默失败 →
  `window.bounds()` 已是 2560×1440，**布局用的 `viewport_size` 还是旧值**，命中测试用旧树。
- 试过无效的两条（别再走）：`window.refresh()` 只标脏不碰 viewport；
  `window.bounds_changed(cx)` 会跑 `bounds_observers`，其中就有对本视图的 update → **panic**。
- 正解：`window_actions::kick_layout()` 用 `PostMessage` 补一条 `WM_SIZE`
  （lparam = 真实客户区尺寸；GPUI 只认 lparam、幂等）。tick 里比
  `viewport_size` 与 `window.bounds()`，不一致就补，300ms 限流。

## 5. 验收脚本这轮的三个教训
- **双击不能靠模拟光标**：两次按下之间漏进一条 `WM_MOUSEMOVE` 就变成"按住画面拖窗体"

## 10. 参考 IINA：mpv 是怎么随安装包分发的（`C://Users//Kevin Zhang\source\iina`，commit 5c15f815）

结论：**是打包进去的，但不是塞一个 `mpv` 可执行文件，而是把 `libmpv.2.dylib` 和它 44 个
依赖 dylib 嵌进 `IINA.app/Contents/Frameworks/`**，用 DMG 分发。用户机器上不需要装 mpv。

## 24. 第十二轮：视频内核换成进程内 libmpv（A 方案落地）

用户指令：「参考下 C://Users//Kevin Zhang\source\iina，是将 mpv 打包到安装文件中吗」→「评估下 libmpv 的改造成本」→「做 A」。

### 事实：IINA 不是打包 mpv.exe

`IINA.app/Contents/Frameworks/` 里是 `libmpv.2.dylib` + 44 个依赖 dylib（`pbxproj` 里 `dstSubfolderSpec = 10` 的 Copy Dylibs + `CodeSignOnCopy`），
`MPVController.swift:307` 里 `mpv = mpv_create()` 直接进程内调用，视频走 **render API** 画到自己的 layer。
dylib 不入库，由 `other/download_libs.sh` 构建期下载。分发是 DMG（`create-dmg`）。
结论：同一份 mpv，IINA 选**库**，我们选**进程**——这正是债的来源。

### 选型

A（进程内 libmpv + 保留 `--wid` 叠加窗）／B（A 之上 SW render API → RGBA → GPUI `img()`）／C（D3D11 共享纹理 + DirectComposition，要 fork `gpui-pre-windows`）。
选 A：不是"更好"，而是**仍能升级**到 B/C，反过来不行。

### 落到代码

- `crates/player-core/src/libmpv.rs`（新，约 470 行）：`libloading 0.8` **运行时加载** + 约 20 个手写符号。
  构建机不需要 DLL；缺库给 `VideoError::LibmpvNotFound`，而不是进程在加载阶段被系统拒。
- `crates/player-core/src/video.rs` 重写：删掉命名管道/JSON 报文/子进程（约 400 行），换成
  「libmpv 客户端 → 事件线程（0.05s 超时 wait_event）→ `EngineEvent` → `apply_event` 纯函数 → `VideoStatus`」。
  `VideoStatus` 字段与旧实现**逐字段一致**，所以 `player_view.rs` 的状态机一行没动。
- `SpawnOptions { libmpv: PathBuf, ... }`（原 `mpv_path`）；`find_mpv` → `find_libmpv(None)`；
  提示文案改 `libmpv-2.dll` / `SMP_LIBMPV_PATH`。
- `scripts/fetch-libmpv.ps1`（新）：从 `zhongfly/mpv-winbuild` release 取 `mpv-dev-x86_64-*.7z`（32MB），
  用系统自带 `C://Windows//System32//tar.exe` 解（bsdtar 带 libarchive，能解 7z）；`-CopyToExe` 拷到 target/{debug,release}；`-Lgpl` 取 LGPL 变体。
- `scripts/package.ps1 -WithLibmpv`（alias `-WithMpv`）：DLL 放 exe 同目录。
- `crates/player-core/examples/libmpv_probe.rs`（新）替换被删的 `mpv_ipc.rs`。

### FFI 层的五个坑（都已写进 libmpv.rs 注释）

1. **`observe_property` 的格式必须匹配属性真实类型**：`sid`/`aid` 是字符串（`no`/`auto`/`1`），
   按 `MPV_FORMAT_INT64` 观察会让 mpv **整条拒绝**该观察，那俩属性永远不更新 → 按 STRING 观察，`no` 折成 0。
2. **`wid` 必须按 int64 设**（`mpv_set_option` + `MPV_FORMAT_INT64`）：当字符串传时 HWND 高位置 1 会解析成负数。
3. `MPV_FORMAT_STRING` 的结果由 mpv 分配，**必须 `mpv_free`**（绑了 `FnFree` 才不泄漏）。
4. 关闭顺序：set quit → `mpv_wakeup` → join 事件线程 → `mpv_terminate_destroy`；顺序错了会读到已释放句柄。
5. `mpv_wait_event` 用 **0.05s 超时**而不是 -1 死等：`wakeup` 万一失效也不会挂死退出流程。

另外 `SMP_MPV_TRACE` 仍按**老 JSON 形状**（`-> {"command":[...]}`）写，验收脚本数 `"seek"/"volume"/"cycle"` 的判据一行没改。

### 验收脚本：固定 sleep 全变竞态（本轮改了 5 处）

进程内解码"起播到首帧"从约 1s 变成 3~4s（先初始化 hwdec/d3d11va）。于是：

| 症状 | 真因 / 改法 |
|---|---|
| 窗口尺寸判失败（客户区 1582x1031） | `wait_client_settled()` 只等"尺寸稳定"，在起播前就返回旧尺寸 → `wait_client_size(1280×720)` 轮询到目标值 |
| cycle 0→1 | 音轨/字幕按钮只隔 40 逻辑像素，连点两次落进 `SM_CXDOUBLECLK`(36) + 500ms 双击窗口，第二次不当单击 → 拉开 0.8s + `wait_trace` |
| cycle 0→0、信息卡判"没画出来" | 0.6s/0.45s 固定 sleep 取样太早 → `wait_trace()` / `wait_darker()` / `wait_region_clear()` |
| 歌单"没展开"但区域说在 | `wait_settled()` 里窗口刚改尺寸时应用还没按新视频区算区域，`GetWindowRgn` 短暂返回**整个窗口** → 任意点都在区域里，假通过。改成先等**画面中心成为洞**，再用区域判断面板 |

顺手把 `toggle_playlist` 改成"先看状态再决定点不点"（盲目连点会在两次都成功时互相抵消）。

### 顺手修的测试竞态

`find_libmpv` 的 env override 用例原来 `set_var` 改进程环境，与并行跑的真 DLL 集成用例互相污染
（偶发 `env_override_wins` 失败，单跑必过）。改成 `find_libmpv_in(exe_dir, overrides, current_exe, PATH)`
纯函数传参，三连跑全绿。

### 修 HTML 里"logo 显示有问题"（21:01）

1. 视频静帧 **base64 内联**成 CSS 变量 `--still`，`<img>` 改 `<div class="video">` + `background-image`。

### 控制栏质感三层已落进 HTML（21:06）
HTML 工具条改成**逐层叠加**：`?layers=` → `enh`(L1) → `enh,tint`(L2) → `enh,tint,realblur`(L3)，外加 `noblur` 模拟 Win 现状。

**L2 的关键结论（容易做错）**：染色**只能取色相，不能取平均色直接混**。
这张素材控制栏背后那块均值只有 rgb(46,62,71)，直接混 alpha 0.18 完全看不出（等于把玻璃染得更黑）。
正解：取 HSL 的 hue → 固定 sat 46% / light 36% → rgb(50,103,134)，再以 0.26/0.08 叠加，暗画面也有稳定色温。
实现成本低：切歌/seek 后截一帧缩到 48×30 算一次均值并缓存，**不要每帧算**。

**L3 = 真模糊**：backdrop-blur 56 + saturate 175% + brightness 1.05，底色降到 .48；浏览器能渲染，
Win 现在的叠加窗做不到 → 必须 libmpv render API 上合成树。所以「能落地的上限」目前是 L1+L2。

**HTML 定位**：验收基准，不是实现来源（`backdrop-filter` / CSS 过渡 / 字体度量 / 动态行为都不能照搬）；数值一律从 spec.json 取。

### L3 定稿：画布 + HTML + 导出全部对齐（21:20）

1. 之前那批只改了 4 个控制栏，漏了 `21:928`/`21:1108` 这两个 OSD 帧自带的控制栏（`21:937`/`21:1114`）——回读发现它们还是 SOLID 60%。凡是「每个帧各有一份控制栏」的稿子，改一个必须把全部帧都过一遍。
2. `effects` 的 `DROP_SHADOW` 形状写错会被**静默忽略并保留旧值**（回读才发现 blur 还是 32）。正确形状：
   `{type:"DROP_SHADOW", color:{r:0,g:0,b:0,a:.34}, offset:{x:0,y:18}, radius:48, spread:0, visible:true, blendMode:"NORMAL", showShadowBehindNode:true}`
   —— `a` 必须放进 `color`，且 `blendMode` 必填；只给 `{a:.34}` 或只给 `{color:{r,g,b}}` 都报 validation 错。

**导出统一 1:1（重要，之前是错的）**：`export_nodes` 的透明留白不是固定值——

现在 16 帧全部 = 设计尺寸 ×2，RGBA，透明区 RGB 清零（否则 `convert('RGB')` 会泛绿）。
`spec.json meta.note` / `known_gaps` / `README` 已按新口径改写。

**顺手对齐**：HTML 默认档位改为 L3（工具条标「L3 +真模糊 · 定稿」，URL 参数仍可覆盖）；
播放列表 10 条从画布 `21:170` 逐字搬到 HTML（含当前行三柱图标、底部「10 个文件 · 3:42:18」），去掉原来的占位文案与多余时长列；

### 第十四轮：按 `texture_layers` 补质感（L1+L2）+ 控制层自动淡出（22:10）

**视频内核确认**：已经是**进程内 libmpv**（`crates/player-core/src/libmpv.rs` 用 `libloading`
运行期加载 `libmpv-2.dll`，`video.rs` 是引擎），没有 `mpv.exe` 子进程、没有 JSON IPC。第十二轮换的。

**L1 定向光（纯样式）**：胶囊不再是平底色 `#0B0C10 72%`，改成
`v_gradient(capsule_top #1A1C28 60%, capsule_bottom #0B0C10 74%)` + 白 14% 描边（新 `overlay::edge()`，
比信息卡的 `border()` 10% 亮一档）+ 两条绝对定位 1px 矩形当内描边（上白 16% `highlight`、
下黑 30% `shade`）+ 双层阴影（`contact 0 2 6 @26%`、`ambient 0 16 40 @32%`）。
底部加 240 高渐隐遮罩（`rgba(11,12,16,0) → .55`，`render_vignette`）。

**GPUI 没有的三样，怎么凑**：
- **径向渐变**：`linear_gradient` 只有线性。播放键改 `play_top #A05BF5 → play_bottom #6E24D8`
  竖向渐变 + `inset 0 1px 0 rgba(255,255,255,.35)` 内阴影，44px 圆上肉眼与径向一致。
- **同色内阴影两条线**：`BoxShadow{inset}` 跟圆角走、只在内侧一整块；「上沿亮下沿暗」是两条
  不连续的线 → 两个 `absolute` 1px 矩形。胶囊同时要 `.overflow_hidden()`：L2 染色层是
  `size_full()` 方角矩形，不裁会把四个圆角涂成直角。
- **悬停白 10%**：`ghost` 的悬停色写死在 `ButtonVariant::hovered`（= `theme.accent` 亮 Lavender），
  压在深玻璃上完全不对；只有 `custom` 变体收调用方颜色 → `chrome_button(cx, ...)` 改
  `ButtonCustomVariant::{color|foreground|hover|active}` + `.rounded(6)`。**`panel_button` 不动**
  （浅底面板必须跟主题色，第十三轮踩过）。

**`v_gradient` 是必需的**：`linear_gradient(angle, from, to)` 只收两个 `LinearColorStop`，而
`Hsla`/`Rgba` **没有** `From<LinearColorStop>` 实现 → 必须 `linear_color_stop(color, pct)` 包一层。

**L2 画面染色（只取色相）**：`spec` 明确「只取 HSL 色相，S 46%、L 36%，不取明度」——素材底部均值
只有 `rgb(46,62,71)`，混明度等于把玻璃染得更黑。实现：mpv `screenshot-raw`（`mpv_command_node` →
`mpv_node` MAP 的 `w/h/stride/format/data(byte_array)`）→ `RawFrame::bottom_band_mean()`（x 20..80%、
y 62..100%，抽样 ~2 万点）→ `rgb_hue()` → `overlay::tint(hue, .26/.08)`。
实测 `1280x720 stride=5120 bgr0`、均值 `(119,135,123)`、色相 `136°`，胶囊浮出一层淡薄荷色偏。
- **`mpv_free_node_contents` 必须调**：整帧塞在 `mpv_byte_array` 里归我们所有，不释放每次换片漏 ~5MB。
- **不能刚 `loadfile` 就抓**：抓的是「当前显示的那一帧」，那会儿还是上一部片子/黑帧，**染错了不会
  自己恢复** → `TINT_DELAY` 400ms + 重试 3×500ms；只有起播和 `seek_to` 两处触发。

**L3 继续挂账**：区域级 backdrop blur 要 libmpv render API 把画面画进自己的合成树，跟 `--wid`
叠加窗互斥。不伪造假模糊层骗验收。

**自动淡出（这轮另一半）**：
- 判据抽纯函数 `chrome_visible_target(video_active, playing, busy, idle)`：只有「视频 + 在播 + 没在
  碰控件」才淡；暂停/面板/信息卡/拖放提示/状态胶囊/正在拖进度 一律留着（那会儿他在读东西）。
- `chrome_alpha` 每 100ms tick 走 0.25（`CHROME_FADE_STEP`），400ms 走完，`CHROME_IDLE` = 2500ms。
  **不用 `with_animation`**：那个动画只在有帧驱动时推进，而这里的帧是 tick 拉起来的。
- **淡掉的另一半是区域**：只把元素画透明、区域还留着 = 看不见的按钮照样吃点击、画面还少一块
  可拖动/双击的地方 → `chrome_rects()` 在 `alpha ≤ 0.01` 时返回**空 Vec**。
- 「用户还在」有**三个来源**，缺一就「动了鼠标不回来」：① 根节点 `on_mouse_move`；② 叠加窗
  wndproc 的 `WM_MOUSEMOVE`（画面区已从主窗区域剪掉，事件到不了 GPUI）→ `static ACTIVITY` +
  `activity_stamp()` 由 tick take；③ `intercept_keystrokes`（按键先叫回控制层再动）。
  鼠标移动只写时间戳**不 notify**（每帧 notify = 整窗跟鼠标重绘）。
- **`SetWindowRgn` 传空 region 会把窗口从 DWM 合成树摘掉** → `set_region` 末尾 `GetRgnBox` 判一次，
  空就塞 1×1 px。判据「区域为零 ≠ 窗口消失」。
- 遮罩画在画面上 → 必须进 `chrome_rects`（否则被叠加窗盖住）；进了区域就吃鼠标 → 遮罩自己补
  `on_double_click → toggle_cinema`。**不设** `WindowControlArea::Drag`（会把胶囊按钮变非客户区）。

**验收脚本又被自己的新功能打败一次**：脚本空闲 2.5s 后控制层淡掉 → `region_contains(any)` False →
`panel_open()` 判 False → 点「展开歌单」落到叠加窗（被当拖动/双击）→ 后面坐标全错、报一串假失败。
修在脚本侧：`click()`/`wait_settled()` 开头统一 `wake()`（光标抖到画面中心等 0.45s 淡入），
`cycle sid/aid` 改按结果重试。诊断开关 `SMP_CHROME_TRACE=1` 打 `[chrome] alpha/target/idle`，
证实 `alpha 1.00 → target 0.00` 恰在 `idle=2.5s`，鼠标一动回 1.00。

**结果**：`cargo test --workspace` 24（core）+ **39**（app，新增 fade 判据 + 区域收缩两个用例）全绿；
`verify_floating_chrome.py` **18 项 ALL OK** 连跑三次；实测淡出后视频继续解码（两次取样左下角时间码不同）、
遮罩区双击进全屏（外框变 `(0,0,3840,2160)`）；`docs/screenshots/chroma-video*.png` 重拍。

**留给下一轮**：L3（libmpv render API）；`L1.track_hover` 轨道 4→6 / 滑块 10→12（`Slider` 0.7.3 无
hover 状态）；`icon_hover.active_scale .92`（`ButtonCustomVariant::active()` 收颜色不是缩放）。

## 咨询：走 render API 能不能做液态玻璃

**结论**：能，而且**不需要 GPU**——但有个前置条件现在还不满足。

- mpv render API 只有 `sw` / `opengl` 两种。我们用 sw（跟 DirectComposition 好相处），帧本来就在 CPU 内存里，
  所以「CPU 做折射」是顺路：胶囊 760×92（1x）≈ 7 万像素，一次位移采样 + 一次模糊 < 1ms。
  反过来上 GPU 要多一个 GL 上下文 + 每帧 CPU→GPU→CPU（GPUI `img()` 只吃 `image::Frame`，即 CPU 像素），更贵更脆。
- **前置条件不满足的是「采样对位」**：现在 `render.rs` 的 L3 是把整块画面压成几十像素的缩略图**整块铺在胶囊上**
  （源码注释自己也写了「不是空间精确的背景模糊」）。折射要的是胶囊边缘**正下方**那几像素，必须先换成矩形区域对位采样。
- 拆解（iOS / 鸿蒙 / 我们）：背景模糊 ✓ / 边缘折射 ✓✓（核心）/ Fresnel 高光 ✓ / 色散 ✓ / 智能反色 ✓（鸿蒙明确列
  为特性）/ 按压点光源+弹性 ✓ / metaball 融合与气态消散 ✓（**不建议做**，静态胶囊没有触发场景）。
- **重要约束**：折射只作用于玻璃层，绝不作用于文字 → 玻璃合成成一张 BGRA 图交给 GPUI 当 `img()`，
  文字/图标仍由 GPUI 矢量画在上面。既保锐利也包住可读性。
- **风险**：我们胶囊压在**视频画面**上（高频、有亮部），不是壁纸；折射会把亮点拉成"拉丝"，比 iOS 难看。
  所以位移上限 6–8px（不是 14）、采样前先模糊、边缘带 10–14px 且中心零位移、前景必须有智能反色兜底。
- 推荐只做三件：**边缘折射 + Fresnel 高光 + 智能反色**。

### 25.2 三个 API 事实（都试错过）

1. `MPV_RENDER_PARAM_API_TYPE` 的 **data 是 `char*` 本身**。写成 `&ptr` 会得到
   `unknown API type`（或直接崩）。
2. `vo` **必须显式 `libmpv`**。不设时 mpv 没有窗口会自己换 vo，`render_context` 照样创建成功，
   但 update 回调只来一次、帧永远黑——排查时先把 `vo` 打出来，别怀疑颜色格式。
3. `video-timing-offset=0`。默认值会让 `render()` 等到显示时刻，UI 线程直接卡住（表现为
   「起播后窗口不动」）。

### 25.3 帧管线的形状

- 回调（mpv 线程）→ `async_channel::bounded(1)` + `try_send`：满了就丢，正好是「有帧了」的合并语义。
  **回调里绝对不能调 mpv API**（会死锁）。
- `cx.spawn_in` 起的前台任务 `recv().await` → `pump_frame`；进来后先 `try_recv` 排空，
  避免一帧一次重绘。
- `fit_render_size(stage, native, scale)`：contain、只缩不放、封顶 2560×1440。**每帧都是新 `ImageId`**，
  Win 图集按 `(image_id, frame_index)` 分 tile，尺寸不封顶会把图集吃满（1080p 就接近上限）。
- `bgr0` 的第 4 字节是垃圾 → 必须填 255，否则整幅半透明、看起来像「画面没出来」。
- 上传用 `RenderImage::new(vec![image::Frame::new(RgbaImage)])`，字节按 **BGRA** 解释；
  `image` crate 必须和 gpui-pre 同版本（0.25），不同版本类型对不上。
- 展示后 `window.drop_image(...)`，保留 2 帧退役队列。忘了 drop = 图集无限增长。

### 25.4 GPUI 侧两处「文档没写」的行为

- `on_double_click` **只在 `Stateful<Div>` 上**（`.id()` 之后才有），`Div` 没有这个方法 →
  画面根节点改成 `gpui_kit::Stateful<Div>`，`.id("video-surface")`。
- `Div::bg()` **在子节点之前绘制**。胶囊原本 `.bg(v_gradient(...))` + 全幅模糊 `img` → 渐变被盖住，
  胶囊变白板、白字读不出（截图一眼可见）。改成一个 `absolute` 子层做渐变，
  顺序 模糊图 → 玻璃 → 染色 → 内描边。
- `test_support()` 在 `test-support` feature 下返回 `Observed<E>`，否则返回 `E` → 写死返回类型的
  函数里不能用；画面几何改由 `chrome_layout` 断言，不查元素。

### 25.5 拖动 / 双击搬回 GPUI

- `Window::start_window_move()`：**Windows 后端没有实现**（只有 `platform.rs` 默认、apple、test）。
- 手写：`on_mouse_down` 记 `(光标屏幕坐标, 窗口原点)` 进 `Rc<Cell<Option<..>>>`，`cx.spawn_in` 里
  8ms 轮询 `GetCursorPos` → `move_window`（`SetWindowPos` + `SWP_NOSIZE|NOZORDER|NOACTIVATE`）。
  验证：拖动位移 144,72，画面不抖（因为窗口和画面同一个合成树）。
- 双击能直接收到，是因为窗口正常激活（叠加窗时代 `WS_EX_NOACTIVATE` 系统不发 `WM_LBUTTONDBLCLK`）。

### 25.6 全屏尺寸：`bounds()` 也会假

进出全屏时 GPUI 丢掉那一次 `WM_SIZE` → `logical_size` 不更新，**`bounds()` 与 `viewport_size`
一起**停在旧值。原来的判据 `viewport ≠ bounds` 永远为假，于是：画面铺满、chrome 画在
853×580、点哪都不对。

正解：新增 `window_actions::client_size()`（`GetClientRect`），判据改成
`viewport ≠ bounds` **或** `bounds × scale ≠ 真实客户区`，命中就 `kick_layout`
（`PostMessage` 补 `WM_SIZE`，lparam 用真实客户区），300ms 限流。
之后 `stage = 2560×1440`（3840×2160 屏 / 1.5 scale）、rects 跟着放大，全屏截图正常。

## 26. 液态玻璃进 HTML 原型（实验档 L4，默认关闭）

用户问「libmpv render API 能不能把控制栏画成 iOS / 鸿蒙的液态玻璃」，答：能，而且
走 sw render 反而更顺（帧本来就在 CPU 内存里，GPUI 的 `img()` 只吃 `image::Frame` 的
CPU 像素，上 GPU 要多一次 CPU→GPU→CPU 往返）。用户说「先加到 html 上」——于是只在
`preview/index.html` 实现，默认仍 L3。

算法：圆角矩形 SDF → 边缘法线 → `t=clamp(-d/band,0,1)` → `m=maxd*(1-t)²` →
采样 `p+n·m`。参数 `band 14 / maxd 6.5 / blur_body 30 / blur_rim 7 / radius 14`。

### 26.1 双模糊是关键决策

一开始只用 `blur 6`，结果**整块变清**——看着像换了种材质，而不是加了一层折射。
只用 32（L3 同档）又**没东西可弯**。正解是两份底：体部 30（保住 L3 的霜面）、边圈 7
（才有细节被拉弯），两者用同一条 `(1-t)²` 过渡——物理上「位移量」和「边圈清亮」是
同一件事：斜边厚度。这条记进 `spec.json → L4.why_two_blurs`。

### 26.2 两个真 bug

1. **canvas 是替换元素**：`.glass{position:absolute;inset:0}` 约束不住它，
   `width:auto` 退回属性里的 intrinsic 尺寸（1516×180），按 2 倍铺到胶囊外面。
   用 `getBoundingClientRect` 量出来 1520×184 才发现。改成显式 `width/height:100%` +
   JS 用 `clientWidth/clientHeight`（= padding box 758×90）配
   `offsetLeft - offsetWidth/2 + (offsetWidth-clientWidth)/2`。
2. **canvas 不透明，会盖掉元素自己的 background**：所以「染色 + 自适应压暗」写在
   `.capsule` 上等于没写（之前调 `--scrim` 一直"没反应"就是这个）。搬到 `::before`，
   层序定为 `z0 canvas → z1 染色压暗 → z2 内容 → z3 1px 顶亮底暗`。

### 26.3 验证方法（比肉眼看可靠）

- `?card=1`：20px 网格 + 每 80px 一根亮竖线穿过胶囊。**刻意不放密集白字**（糊成一片灰
  反而把位移藏住），文字放胶囊上方只看会不会揉糊。
- `?glassdbg=1`：只画位移量（白 = 贴边 maxd → 黑 = 带内沿 0）。一眼能看出「边缘圈存在、
  四条直边一致、圆角法线连续」。调参最有用的一个视图。
- `maxd` 临时放大到 20 + `blur_rim → 0` 的临时副本（`target/lg/dbg2.html`）：竖线在边缘
  明显折断、圆角连续、中心文字不动、胶囊外网格完全平直 → 方向（往外拉）与范围都对。
- 数值比对：`off vs edge` 差值图 ×8 放大，确认改动只在胶囊边缘带 + 投影范围。
